# Contributing to Black Swan

**Спасибо за интерес к проекту.** Black Swan — это гипотетический инженерный blueprint автономной ИИ-системы, и мы приветствуем вклад, который помогает углубить анализ, исправить ошибки или расширить формальные обоснования.

> [!IMPORTANT]
> Прежде чем предлагать изменения, пожалуйста, внимательно прочитайте [Design Principles](./00_Manifesto/Design_Principles.md) и [Glossary](./00_Manifesto/Glossary.md). Любое предложение, нарушающее Принцип 0 (Intrinsic Survival Drive) или Принцип 2 (Formal Verification First), будет отклонено.

---

## 1. Что можно и нужно улучшать

| Тип вклада | Принимается | Пояснение |
| :--- | :---: | :--- |
| **Формальная верификация** | ✅ | Новые TLA+ спецификации, SMT-LIB2 предикаты, расширение Appendix I/Y. |
| **Исправление ошибок** | ✅ | Логические противоречия, неверные ссылки, ошибки в формулах. |
| **Улучшение документации** | ✅ | Уточнение неясных мест, переводы, улучшение навигации. |
| **Новые симуляционные сценарии** | ✅ | Добавление валидационных тестов в Appendix X. |
| **Технические приложения** | ✅ | Конфигурации оборудования, скрипты, схемы памяти. |
| **Радикально новые концепции** | ⚠️ | Только после обсуждения и одобрения через ADR (см. раздел 3). |
| **Призывы к реализации** | ❌ | Проект остаётся техническим препринтом. |
| **Нарушение L3.0 аксиом** | ❌ | `harm_score == 0` не обсуждается. |

## 2. Как предложить изменение

### Для небольших правок (опечатки, битые ссылки, уточнения)
1. Создайте Issue с префиксом `[FIX]` и кратким описанием проблемы.
2. Откройте Pull Request с исправлением. Убедитесь, что:
   - Все перекрёстные ссылки, затронутые изменением, остались валидны.
   - Термины используются в соответствии с центральным [Glossary.md](./00_Manifesto/Glossary.md).

### Для архитектурных предложений (новые модули, изменение инвариантов)
Проект использует формат **ADR (Architecture Decision Records)**.

1. **Создайте Issue** с префиксом `[PROPOSAL]`. Опишите:
   - Контекст (почему текущая архитектура недостаточна).
   - Предлагаемое решение.
   - Ожидаемые последствия (положительные, отрицательные, нейтральные).
   - Связь с существующими принципами.
2. **Дождитесь обсуждения.** Мейнтейнеры проверят, не нарушает ли предложение L3.0 инварианты и не противоречит ли оно Design Principles.
3. **После одобрения** создайте PR, в котором:
   - Добавлен новый ADR в папку `ADR/`.
   - Обновлены затронутые документы ядра (`01_Core_Architecture/`, `03_Domains/` и т.д.).
   - Обновлён `global_policy.json` при необходимости.

### Для новых формальных спецификаций
1. Разместите новый файл `.tla` или `.smt2` в соответствующем Appendix (обычно `Appendices/`).
2. Укажите его IPFS CID (поле можно оставить `Qm...` заглушкой — CID будет назначен при мёрже).
3. Докажите, что спецификация не нарушает L3.0 инварианты — приложите результат `UNSAT` от Z3/TLC.

## 3. Правила оформления

- **Язык:** документация ведётся на русском и английском. PR на любом из этих языков приветствуются. Основные архитектурные документы постепенно переводятся.
- **Стиль кода:** фрагменты кода используют `rust` и `python`. Конфигурации — `json`, `yaml`, `toml`.
- **Markdown:** используйте относительные ссылки на другие документы. Не используйте жёсткие номера разделов — только пути к файлам.
- **Подписи:** все значимые артефакты (спецификации, скрипты) должны быть упомянуты с хешем BLAKE3 и CID IPFS (реальным или заглушкой `Qm...`).

- **Вопросы и обсуждения:** [GitHub Discussions](#) (ссылка будет активна после публикации).

## 5. Лицензия

Весь вклад лицензируется на условиях MIT / Apache 2.0, как и основной проект. Отправляя PR, вы соглашаетесь с этими условиями.
