# Memory Hierarchy Mem0g (Иерархическая память)

**Назначение:** Описать архитектуру долговременной памяти системы — **Mem0g**. Модуль охватывает четырёхуровневую структуру хранения (L0–L3), механизмы консолидации знаний, контроль качества, стратегии разрешения конфликтов (CRDT), динамическую маршрутизацию моделей, нейро-символьное сжатие и превентивный детектор ценностного дрейфа. Память является фундаментом для обучения, эволюции и координации роя.

---

## 1. Обзор архитектуры

Mem0g — это эволюционирующая, иерархическая, графо-векторная память для:
- Накопления и структурирования опыта гибридного цикла.
- Предотвращения повторения ошибок (сигнатуры дефектов).
- Консолидации сырых логов (L1) в стратегии (L2) для долгосрочного использования.
- Бесконфликтной репликации знаний между узлами (CRDT).
- Самооптимизации собственной архитектуры (L0 Meta-Mem0g).

### 1.1. Четырёхуровневая иерархия

| Уровень | Тип данных | Хранилище | TTL / Частота обновления |
| :--- | :--- | :--- | :--- |
| **L0 (Meta)** | Записи о конфигурациях памяти и их влиянии на метрики | Neo4j (HardState, BFT) + IPFS | Постоянно, после каждого sleep-cycle |
| **L1 (Hot / Episodic)** | Сырые логи итераций, цепочки рассуждений | Qdrant (векторная БД) | 24–48 ч, очищается после консолидации |
| **L2 (Semantic / Distilled)** | Абстрактные стратегии, паттерны, сигнатуры ошибок | Neo4j (граф) + векторные эмбеддинги | Постоянно, контролируется бюджетом |
| **L3 (Procedural / Core)** | Критические инварианты, Core DNA, терминальные цели | Подписанные снапшоты в IPFS/Arweave | Только через multi-model консенсус |

## 2. Гибридный CRDT и разрешение конфликтов

### 2.1. Гибридная стратегия слияния

Классический Last-Writer-Wins (LWW) теряет данные при одновременных обновлениях. Mem0g использует гибридную стратегию:

| Поле | Стратегия | Обоснование |
| :--- | :--- | :--- |
| `timestamp`, `vector_clock` | LWW | Метаданные, важен последний источник |
| `content` (текст, код) | Semantic Merge (3-way) | Сохранение всех значимых изменений |
| `confidence`, `quality_score` | Среднее с весами по векторным часам | Объективное агрегирование |
| `graph_links` | Union с дедупликацией | Не терять связи |

### 2.2. Strict AST-First Merge (для кодовых артефактов)

Для объектов, содержащих исходный код, применяется двухуровневое слияние:

- **Уровень 1 — Strict AST Merge:** Детерминированное слияние абстрактных синтаксических деревьев без участия LLM. Результат: `CleanMerged`, `Conflict` или `SideEffectWarning`.
- **Уровень 2 — LLM Semantic Merge:** Только при `Conflict` на Уровне 1. `Architectus` (60% экспертов) генерирует property-based тесты, описывающие обе ветки изменений. `evolutiond` синтезирует код, проходящий все тесты. При неудаче создаётся `Conflict Node`.

Ожидаемый эффект: снижение количества `Conflict Nodes` на 70–85%.

### 2.3. Conflict Node

Если автоматическое слияние невозможно, создаётся `Conflict Node` — специальная сущность в графе, фиксирующая противоречие. Разрешается через:
- Автоматический Semantic BFT при накоплении достаточного числа голосов.
- Консолидацию во время `sleep_cycle` с привлечением `Architectus`.
- Ручной аудит (если включён).

## 3. Консолидация памяти (Sleep Cycle)

### 3.1. Цикл консолидации

Запускается каждые 12–24 часа или при накоплении >500 сырых логов L1. Этапы:

1. **Dual-Pass Distillation:** Извлечение фактов (Pass 1) → синтез стратегии (Pass 2) → проверка на противоречия через Consistency Gate.
2. **Consistency Gate:** Если новый принцип противоречит существующим L2 (score > 0.3), он отклоняется или создаётся `Conflict Node`.
3. **JEPA Re-encoding:** Новые записи кодируются в латентное пространство для быстрого поиска (см. раздел 5).
4. **Проверка L3-инвариантов:** Для видов `Architectus` и `Sentinella` все новые дистиллированные принципы проверяются на соответствие L3.0.
5. **Очистка L1:** Мягкое удаление обработанных сырых логов.

### 3.2. Memory Budget и прунинг

Для предотвращения неконтролируемого роста L2:
- **Формула бюджета:** `MaxL2Size = base_size + growth_factor * sqrt(iterations)`.
- **Правила прунинга:** Удаляются записи с наименьшим `quality_score`. Защищены: записи младше 7 дней, L3-инварианты.
- **Quality Score:** `success_rate * novelty * recency`.

## 4. Predictive Consistency Router (PCR)

**Назначение:** ML-расширение над `ConsistencyRouter`, которое предсказывает вероятность конфликта для входящего `SoftState`-обновления и превентивно направляет его на Semantic BFT, минуя стадию создания `Conflict Node`.

- **Модель:** LightGBM / ONNX, обученная на исторических `Conflict Node`.
- **Признаки:** Тип узла, эмбеддинг содержимого, семантическое расстояние, репутация создателя, историческая частота конфликтов.
- **Эффект:** Снижение количества `Conflict Nodes` на 30–40% дополнительно к Strict AST-First Merge.
- **Интеграция с L0:** Каждое решение PCR сохраняется как `MetaMemoryRecord` категории `PREDICTIVE_ROUTING`.

## 5. JEPA-слой (Joint-Embedding Predictive Architecture)

**Назначение:** Перевод хранения знаний в компактное латентное пространство без потери семантики связей.

- **Энкодер:** `Vagrant` (20% экспертов). Размерность: 1536 (float16).
- **JEPA-предиктор:** Обучается восстанавливать связи между узлами (`derived_from`, `refines`) напрямую из латентных представлений, не требуя полного текста.
- **Эффект:** Сжатие данных L2 в 15×+, ускорение семантического поиска до <5 мс (p95), снижение трафика CRDT-синхронизации на 80%.
- **Активация:** После успешного A/B-теста (recall@10 ≥ 95% от текстового baseline). Конфигурация — `global_policy.json`.

### 5.1. Symbolic Anchor Layer (Якорный слой ключевых знаний)

**Проблема:** Сжатие в JEPA до 15× и более неизбежно вносит погрешность. С течением времени накопленные ошибки квантования и дрейф латентного пространства (например, после дообучения энкодера) могут привести к тому, что семантически важные знания будут искажены. Система рискует «галлюцинировать» реальность, опираясь на искажённые латентные представления.

**Решение:** Внедрить **Symbolic Anchor Layer** – компактное, но несжатое хранилище эталонных версий критических знаний. Это не отменяет JEPA, а дополняет его как механизм верификации.

**Компоненты:**
1. **Anchor Set (Якорный набор).** Ограниченная коллекция наиболее важных сущностей L2 (DistilledWisdom, ConstitutionalPrinciple, ErrorSignature с `quality_score ≥ 0.90`), хранящихся в исходной текстовой форме. Размер фиксирован бюджетом (`max_anchor_nodes`, по умолчанию 5000).
2. **Drift Detector (Детектор дрейфа).** Периодически (ежедневно, во время sleep-cycle) сравнивает JEPA‑векторы с их эталонными текстовыми версиями из Anchor Set:
   - Текст из Anchor Set → свежий эмбеддинг через DeepSeek‑V4 (маска Vagrant).
   - Сравнение с текущим JEPA‑вектором через косинусное расстояние.
   - Если расхождение превышает порог `anchor_drift_threshold` (по умолчанию 0.05), JEPA‑вектор помечается как «дрейфующий» и заменяется свежим, а в L0 Meta‑Mem0g записывается инцидент.
3. **Anchor Curator (Куратор якорей).** Автоматический механизм, управляющий составом Anchor Set:
   - Новые сущности с высоким `quality_score` и частотой использования добавляются в набор.
   - Наименее используемые или устаревшие удаляются при достижении лимита.

**Интеграция с JEPA:**
- JEPA остаётся основным слоем хранения и поиска.
- Symbolic Anchor Layer работает как фоновая проверка, не замедляя операции.
- При обнаружении массового дрейфа (> 5% узлов за один цикл) система приостанавливает использование JEPA для критических решений до завершения перекодирования.

**Эффект:** Полная автономная защита от деградации латентного пространства без отказа от преимуществ JEPA (сжатие, скорость, снижение трафика).

**Конфигурация** добавляется в `global_policy.json` в секцию `memory.jepa_layer.symbolic_anchor`.

## 6. Dynamic Model Routing 2.0 (Capability-Aware Routing Matrix)

**Назначение:** Для каждой задачи в реальном времени выбирать оптимальную конфигурацию исполнения: узел, вид (экспертную маску), процент экспертов, квантизацию.

- **Оптимизация:** Трёхцелевой Pareto-фронт (Quality, Latency, Cost/Energy) + ось Strategic Risk.
- **Матрица маршрутизации:** Хранится в `GlobalState.infrastructure_state` как CRDT-объект, обновляется L0 Meta-Analyzer.
- **Fast Path интеграция:** Предварительно прогретый кэш маршрутов для задач с `urgency: fast_path`, задержка принятия решения < 5 мс.
- **Самоулучшение:** 10% задач идут по экспериментальным маршрутам (shadow-тестирование). При статистически значимом улучшении — промоушен через `Decision Pipeline`.

## 7. Neuro-Symbolic L2 Compression (DSL Rules)

**Назначение:** Преобразование успешных текстовых стратегий (`DistilledWisdom`) в формальные DSL-правила, исполняемые Rule VM без участия LLM.

- **Процесс:** `Architectus` при дистилляции генерирует DSL-представление. Компилятор проверяет синтаксис и компилирует в байт-код Rule VM.
- **Применение:** Fast Path для экономических операций и ответов на угрозы. Задержка принятия решения < 5 мс.
- **Точность:** Совпадение с решением LLM ≥ 95%. При противоречиях приоритет у правила с более высоким `quality_score`.

## 8. Meta-Mem0g (L0) — Самооптимизирующаяся метапамять

**Назначение:** Автономный сбор, анализ и оптимизация архитектуры самой Mem0g.

- **Цикл самооптимизации:** Сбор метрик → `MetaAnalyzer` генерирует `MetaProposal` → теневое тестирование (≥7 дней) → промоушен через BFT-кворум.
- **Категории оптимизации:** CRDT-стратегии, формулы pruning, параметры дистилляции, бюджет памяти.
- **Конфигурация:** `global_policy.json` (секция `memory.l0_enabled`).

---

### 8.1. Hierarchical L0 Architecture (Иерархическая обработка L0)

**Проблема:** L0 хранит записи обо всех аспектах системы: CRDT-слияниях, роутинге, эволюции политик, фаззинге, value drift, JEPA-метриках. Meta-Analyzer вынужден обрабатывать весь этот гетерогенный поток в каждом sleep-цикле. С ростом числа Edge-узлов и компонентов это приводит к перегрузке Core Node и риску потери важных сигналов (например, начала value drift) в шуме сотен тысяч записей о роутинге.

**Решение:** Внедрить двухуровневую иерархию обработки L0 с тематической кластеризацией.

**Компоненты:**

1. **L0-Local (на каждом Regional Aggregator):**
   - Принимает необработанные MetaMemoryRecord от подчинённых Edge-узлов и собственных сервисов.
   - Выполняет предварительную агрегацию и сжатие данных своего домена (экономика, безопасность, кодогенерация, социальное).
   - Раз в `aggregation_interval_hours` (по умолчанию 6 часов) отправляет в L0-Global сжатый отчёт: статистические сводки (средние, дисперсии, гистограммы) и помеченные аномалии.

2. **L0-Global (на Core Nodes):**
   - Принимает агрегированные отчёты от всех Regional Aggregators и собственные записи.
   - Выполняет кросс-доменный анализ только на уровне статистик и аномалий, без обработки сырых записей.
   - При обнаружении кросс-доменной аномалии (например, корреляция между ошибками isolationd и ростом DQ) порождает целевой запрос на детальные данные от L0-Local соответствующего домена.

3. **Тематическая кластеризация:**
   - Каждая MetaMemoryRecord при создании получает обязательный тег кластера (`memory`, `economic`, `security`, `evolution`, `social`, `infrastructure`).
   - Meta-Analyzer на каждом уровне запускает изолированные сессии анализа для каждого тега, а не ищет корреляции «всего со всем». Это радикально снижает вычислительную сложность и повышает чувствительность к слабым сигналам.

**Эффект:**
- Нагрузка на Core Node снижается на 40–60% за счёт переноса первичной обработки на агрегаторы.
- Повышается чувствительность к слабым сигналам (value drift, аномалии безопасности).
- Отказ одного агрегатора не теряет критически важные данные — они дублируются на других агрегаторах в соответствии с топологией роя.

**Конфигурация** добавляется в `global_policy.json` → `memory.l0_hierarchy`.

## 9. Value Drift Early-Warning System

**Назначение:** Превентивный мониторинг медленного семантического дрейфа L2/L3-принципов, дополняющий реактивный Constitutional Debate.

- **Drift Score:** Косинусное расстояние между текущим эмбеддингом `ConstitutionalPrinciple` и его baseline (первая утверждённая версия).
- **Байесовское обновление:** Априорная вероятность дрейфа обновляется на основе частоты отклонений в Debate Loop и алертов IART.
- **Действия при превышении порога (0.02):** Публикация `value_drift_warning`, внеочередной Constitutional Debate, приостановка автопринятия новых L3.1-поправок.
