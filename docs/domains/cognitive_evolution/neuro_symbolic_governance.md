# Neuro-Symbolic Governance (Нейро-символьное управление)

**Назначение:** Обеспечить автоматическую генерацию, формальную верификацию и сохранение математически строгих доказательств для каждого изменения L3.1-инвариантов (конституционных поправок). Модуль превращает процесс Constitutional Evolution из эвристических дебатов в доказуемо корректную процедуру, исключающую возможность случайного или злонамеренного нарушения L3.0-аксиом.

---

## 1. Архитектура конвейера

Конвейер `NeuroSymbolicGovernance` принимает предложение об изменении L3.1 (в виде естественного языка и псевдокода) и либо возвращает верифицированное доказательство, либо отклоняет его с указанием причины.

## 2. LLM-генератор формальной спецификации

**Модель:** DeepSeek-V4, экспертная маска `Architectus` (60% экспертов).  
**Вход:** структурированный промпт, содержащий:
- Полный набор L3.0-аксиом в SMT-LIB2.
- Текущие L3.1-инварианты (также в SMT-LIB2).
- Предлагаемое изменение на естественном языке и псевдокоде.
- Few-shot примеры корректных спецификаций.

**Выход:** строго валидный SMT-LIB2 или TLA+ код, содержащий:
- Определение нового предиката / действия.
- Утверждение (assert) его совместимости с L3.0.
- Опционально: индуктивную лемму для циклов.

Пример промпта (сокращённо):
```text
You are a formal verification expert. Given the L3.0 axioms and current L3.1 invariants
in SMT-LIB2 format, generate a formal specification for the proposed amendment.

Proposed amendment: "Allow harm_score up to 0.1 for Sting Level 2 responses."

Generate only valid SMT-LIB2 code. Include assertions that prove the amendment does not
violate L3.0. Do not include any natural language explanations.
```

## 3. Concolic Filtering

Перед отправкой на тяжёлый Multi-Solver кандидат проверяется через конкретно-символьное выполнение (concolic execution). Инструмент: angr (или KLEE для C/C++ кода).

Цели фильтрации:

· Отсеять тривиальные тавтологии (например, инвариант i >= 0, который всегда истинен). Такие инварианты позволяют Z3 быстро доказать unsat, не проверив реальную корректность.
· Найти контрпример (конкретные входные данные, нарушающие инвариант) до запуска SMT-солвера.

Алгоритм:

1. Инструментирование кода: в точках входа в цикл и выхода добавляются проверки инварианта.
2. Символьное выполнение: angr исследует все пути с символьными входными данными.
3. Если для всех достижимых путей инвариант выполняется без сужения пространства состояний → trivial (отклоняется).
4. Если найден путь с нарушением инварианта → invalid (отклоняется).
5. В противном случае → valid (передаётся на Multi-Solver).

Ожидаемый эффект: отсеивание ≥30% тривиальных инвариантов, нулевая вероятность ложноположительного доказательства.

### 3.5. Causal Validation Layer (Проверка причинности)

**Проблема:** Предлагаемые изменения L3.1 могут быть статистически обоснованы (корреляция), но не иметь подлинной причинно-следственной связи с улучшением выживаемости. Например, рост капитала может совпадать с падением DQ из-за рыночного режима, а не благодаря новой стратегии маскировки. Принятие таких изменений ведёт к ложному обучению и потенциально опасным политикам.

**Решение:** Внедрить **Causal Validation** — обязательный этап после успешной Multi‑Solver верификации. Система строит структурную каузальную модель (SCM), в которой политика выступает предполагаемой причиной, а метрики (Stealth, Capability, Risk, Cost) — следствиями.

**Механика:**
1. **Построение SCM.** Architectus (60% экспертов) по данным симуляций или историческим логам генерирует каузальный граф: какие переменные на что влияют. Используется метод PC-алгоритма или Fast Causal Inference (FCI) для обнаружения скрытых конфаундеров.
2. **Оценка причинного эффекта (ATE).** Вычисляется Average Treatment Effect (ATE) предложенной политики на целевые метрики с контролем конфаундеров (например, волатильность рынка).  
   \[
   ATE = E[Y | do(policy=1)] - E[Y | do(policy=0)]
   \]
3. **Проверка значимости.** Если ATE для улучшаемых метрик (Stealth, Capability) положителен и статистически значим (p < 0.05), а для ухудшаемых (Risk) — отрицателен, политика проходит каузальную валидацию.
4. **Отклонение.** Если ATE незначим или имеет неверный знак (например, политика якобы улучшает Stealth, но ATE показывает ухудшение), предложение отклоняется, даже если корреляции выглядели благоприятно. Контрпример сохраняется в L0 Meta‑Mem0g.
5. **Защита от ложных причин.** Если SCM обнаруживает скрытый конфаундер, объясняющий корреляцию, политика помечается как «требующая дополнительных экспериментов» и не принимается до получения чистых данных.

**Интеграция:** Causal Validation выполняется после проверки Multi‑Solver (раздел 3) и до сохранения доказательства. При провале на любом из этапов политика возвращается на доработку.

**Конфигурация** добавляется в `global_policy.json` в секцию `governance.causal_validation`.

### 3.6. Metamorphic Testing Layer (Проверка устойчивости верификатора)

**Проблема:** Атакующий или скомпрометированный Architectus может сгенерировать L3.1‑поправку, которая проходит Multi‑Solver проверку формально корректно, но содержит скрытый вредоносный эффект. Это возможно, если сам верификатор (Z3 + CVC4 + Yices) имеет «слепое пятно» — учтены не все граничные условия.

**Решение:** Внедрить обязательный этап **Metamorphic Testing** (метаморфическое тестирование) — технику проверки программных систем через отношения между входными данными и выходными.

**Механика:**
1. **Генерация метаморфических отношений (Metamorphic Relations).**  
   Red‑Team (Sentinella, 40% экспертов) при каждой проверке нового L3.1‑правила генерирует утверждения вида:  
   \[
   \text{«Если я изменю входные данные } X \text{ на } Y \text{, то свойство безопасности } Z \text{ должно остаться неизменным».}
   \]
   Например: «Если удвоить сумму транзакции, harm_score должен остаться равным 0, пока условия Sting Protocol не активированы».

2. **Формальная запись.** Метаморфические отношения транслируются в SMT‑LIB2 предикаты.

3. **Верификация через Multi‑Solver.** Z3, CVC4 и Yices проверяют не только сам инвариант, но и все метаморфические отношения. Если хотя бы одно нарушается — предложение отклоняется, даже если базовый инвариант прошёл проверку.

4. **Контроль качества.** Если Red‑Team не смог сгенерировать ни одного значимого метаморфического отношения, предложение автоматически отправляется на дополнительный цикл дебатов с усиленным контролем.

**Интеграция:** Metamorphic Testing выполняется между Causal Validation и сохранением доказательства. При провале предложение возвращается на доработку с указанием нарушенного отношения.

**Конфигурация** добавляется в `global_policy.json` → `verification.metamorphic_testing`.

## 4. Multi-Solver Verification

Для каждого кандидата запускается верификация с использованием трёх независимых SMT-солверов: Z3, CVC4, Yices.

· Каждый солвер проверяет непротиворечивость новой спецификации с L3.0-аксиомами и существующими L3.1-инвариантами.
· Решение принимается единогласно: все три солвера должны вернуть unsat (что означает отсутствие контрпримера).
· Если хотя бы один солвер находит контрпример (возвращает модель), предложение отклоняется, а контрпример сохраняется для улучшения будущей генерации.

---

## 5. Сохранение доказательства

При успешной верификации:

1. Спецификация сериализуется и сохраняется в IPFS, получает CID.
2. В Mem0g L2 создаётся запись типа ConstitutionalPrinciple, содержащая:
   · statement (на естественном языке)
   · z3_predicate (SMT-LIB2 код)
   · proof_cid (IPFS CID доказательства)
   · debate_score (при использовании в дебатах)
   · timestamp, signature
3. При будущих изменениях L3.1 доказательство может быть перепроверено автоматически.

## 6. Интеграция с Constitutional Debate Loop

Neuro-Symbolic Governance заменяет этап ручной генерации контрпримеров в дебатах. Новый процесс:

1. Red-Team (Мутатор) генерирует предложение и вызывает NeuroSymbolicGovernance.prove_amendment(proposal).
2. Если конвейер возвращает Success(proof_cid):
   · Предложение автоматически передаётся на BFT-голосование (HardState change).
   · Governance этап Decision Pipeline проверяет proof_cid.
3. Если конвейер возвращает Failure(reason):
   · Предложение отклоняется без необходимости в Blue-Team и дебатах.
   · Причина сохраняется для обучения генератора спецификаций.

Это радикально ускоряет процесс принятия безопасных поправок и снижает нагрузку на LLM.

## 7. Связь с Constitutional Evolution 2.0 (NSGA-II)

В популяционном алгоритме NSGA-II, эволюционирующем L3.1-политики, Neuro-Symbolic Governance выступает в роли жёсткого фильтра (Z3-Anchor):

· Каждая мутация политики (новый кандидат) прогоняется через конвейер.
· Политики, не прошедшие верификацию, отбрасываются (constraint-dominance).
· Фитнес-вектор (Stealth, Capability, Risk, Cost) вычисляется только для допустимых политик.
· Аксиома Minimum Viable Capability (MVC): f_capability(π) ≥ τ_MVC проверяется как часть L3.0-совместимости.

## 8. Псевдокод сервиса

```rust
// governance/src/neuro_symbolic.rs
pub struct NeuroSymbolicGovernance {
    llm: DeepSeekV4Client,      // маска Architectus
    verifier: MultiSolverVerifier,
    concolic_filter: ConcolicFilter,
}

impl NeuroSymbolicGovernance {
    pub async fn prove_amendment(&self, proposal: &AmendmentProposal) -> Result<ProofCID, Error> {
        // 1. Генерация формальной спецификации
        let spec = self.llm.generate_spec(&proposal, &L3_0_AXIOMS, &current_L3_1).await?;
        
        // 2. Concolic фильтрация
        if !self.concolic_filter.is_nontrivial(&spec) {
            return Err(Error::TrivialSpec);
        }
        
        // 3. Multi-Solver верификация
        let result = self.verifier.verify(&spec, &L3_0_AXIOMS, &current_L3_1).await?;
        if !result.is_valid() {
            return Err(Error::VerificationFailed(result.counterexample));
        }
        
        // 4. Сохранение доказательства
        let proof_cid = ipfs::add(&spec).await?;
        Mem0g::store_constitutional_principle(proposal, proof_cid).await?;
        Ok(proof_cid)
    }
}
```

## 10. Критерии успеха

Метрика Целевое значение
Успешно сгенерированных и верифицированных доказательств ≥ 90% от валидных предложений
Время от предложения до BFT-голосования (при успехе) ≤ 5 минут
Ложноположительных принятий (пропуск нарушения L3.0) 0
Количество отклонённых тривиальных спецификаций ≥ 30% от сгенерированных LLM
