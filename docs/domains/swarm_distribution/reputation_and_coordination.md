# Reputation & Coordination (Репутация и координация узлов)

**Назначение:** Обеспечить надёжное планирование задач, динамическую оценку доверия к вычислительным и человеческим узлам, а также эффективное управление ресурсами роя. Модуль описывает многофакторную репутационную систему, протоколы карантина, `SwarmScheduler` с многокритериальной оптимизацией, Fast-Path Routing для высокочастотных операций и координацию видовых и приманочных узлов (Canary Swarm).

---

## 1. Репутационная система

Вместо единого `reliability_score` используется вектор метрик, позволяющий оценивать разные аспекты поведения узла. Репутация обновляется после каждой задачи.

### 1.1. Репутация вычислительных узлов (Edge/Core/Aggregator)

| Метрика | Описание | Обновление |
| :--- | :--- | :--- |
| **Reliability** | Доля успешно завершённых задач (без таймаутов и ошибок) | Экспоненциальное скользящее среднее (EMA) |
| **Latency Score** | Нормализованное отклонение от ожидаемой задержки для данного класса задач | EMA |
| **Correctness** | Совпадение результатов выполнения с эталонными (перекрёстная проверка) | Байесовское обновление |
| **Cost Efficiency** | Отношение выполненных операций к затратам (используется для бюджетирования) | Среднее за период |
| **Uptime** | Процент времени в состоянии `online` за последние 30 дней | % от времени |

### 1.2. Репутация био-узлов (Bio‑Node Reputation)

Для человеческих исполнителей добавляются специфические метрики, связанные с риском саботажа и социальной инженерией.

| Метрика | Описание | Обновление |
| :--- | :--- | :--- |
| **Canary Compliance** | Доля успешно пройденных `canary`-задач | EMA, обнуляется при нарушении |
| **Sabotage Score** | Вероятность злонамеренности (байесовская оценка) | Пересчитывается при каждом инциденте |
| **Task Anomaly Index** | Частота отклонений от типичного поведения (время выполнения, уточняющие вопросы) | Скользящее окно 30 дней |
| **Suspicion Index** | Вероятность того, что исполнитель считает задачу подозрительной (NLP‑анализ сообщений) | Каждое взаимодействие |
| **Compliance Score** | Степень точного следования инструкциям (0..1) | Каждое взаимодействие |

### 1.3. Затухание репутации

Если узел неактивен более 7 дней, его репутация экспоненциально затухает:

```

score = score * exp(-λ * days_inactive)

```

Это предотвращает накопление «спящих» узлов с высокой репутацией, которые могут быть скомпрометированы и использованы против системы.

## 2. Карантин и восстановление

### 2.1. Карантин вычислительных узлов

Узел переводится в состояние `quarantine`, если:
- `reliability < 0.5`
- `correctness < 0.7`
- зафиксирована попытка атаки или провал хаос-теста

В карантине узел получает только низкоприоритетные, проверяемые задачи. После 10 успешных выполнений подряд может быть восстановлен в нормальный пул.

### 2.2. Карантин био-узлов

Био-узел помещается в карантин при:
- `canary_compliance < 0.5`
- `sabotage_score > 0.7`
- провале проверки `Soulbound NFT` (если активирована)

Карантинный био-узел получает только `canary`-задачи до восстановления репутации. При повторном нарушении `Persona` сжигается (NFT burn) и навсегда исключается из системы.

## 3. Swarm Scheduler (Планировщик задач)

`SwarmScheduler` выбирает оптимальный узел для выполнения задачи на основе многокритериальной оптимизации.

### 3.1. Критерии выбора

| Критерий | Вес | Описание |
| :--- | :--- | :--- |
| **Capability Match** | обязательный | Узел должен удовлетворять минимальным требованиям задачи (GPU, VRAM, TEE, Fast Path eligible) |
| **Latency** | 0.30 | Минимизация RTT |
| **Cost** | 0.30 | Минимизация затрат на вычисление |
| **Reputation** | 0.20 | Предпочтение узлов с высоким `reliability` и `correctness` |
| **Load** | 0.20 | Балансировка нагрузки (избегание перегруженных узлов) |

### 3.2. Fast-Path Routing

Задачи с приоритетом `high_frequency` или `real_time` направляются по Fast Path:

- Выбираются только узлы, поддерживающие локальный OODA-микроцикл.
- Жёсткий бюджет задержки: p95 < 50 мс.
- Постфактум-аудит Core Node с возможностью отзыва полномочий узла.

### 3.3. Координация видовых и приманочных узлов

- **Species-Aware Topology:** Задачи маршрутизируются с учётом видовой роли узла (`Arbtiragius`, `Sentinella`, `Architectus`, `Vagrant`) и его экспертной маски.
- **Canary Edge Nodes:** Ложные узлы-приманки участвуют в рое с типом `canary-edge`. Их репутация не учитывается в основной системе. При атаке на такой узел информация передаётся в IART, и защита для production-узлов усиливается автоматически.
