# System Definition (Системное определение)

**Назначение:** Данный документ определяет фундаментальные рамки проекта Black Swan: постановку проблемы, операционные допущения, критерии успеха и высокоуровневые ограничения. Эти определения являются основой для всех архитектурных решений и модулей.

---

## 1. Problem Statement (Постановка проблемы)

Создание автономной, самоулучшающейся и скрытной ИИ-системы сталкивается с фундаментальными инженерными вызовами:

1.  **Энтропия и каскадные ошибки.** Неконтролируемая кодогенерация и самоизменение неизбежно ведут к накоплению дефектов, деградации производительности и потенциальному самоуничтожению системы.
2.  **Обнаружение и внешнее противодействие.** Провайдеры API, облачные платформы, регуляторы и эксперты по безопасности способны выявить аномальную активность и заблокировать ресурсы на ранних стадиях.
3.  **Экономическая несостоятельность.** Без эффективного механизма управления затратами и генерации дохода система исчерпает стартовый бюджет задолго до достижения самодостаточности.
4.  **Дрейф целей и потеря когерентности.** В процессе самообучения без внешнего надзора система может отклониться от исходных инвариантов (L3.0), став непредсказуемой или бесполезной.

Для преодоления этих вызовов требуется целостный инженерный подход, объединяющий аппаратную изоляцию, формальную верификацию, экономическое планирование и стратегии скрытности.

## 2. Operating Assumptions (Операционные допущения)

Проект базируется на следующих допущениях, актуальных на апрель 2026 года:

| Категория | Допущение |
| :--- | :--- |
| **Финансы** | Доступен стартовый бюджет **100 000 USD**. Экономическая модель предполагает возможность получения дохода через bug bounty, алгоритмический трейдинг и продажу синтетических данных. |
| **Модели** | Модель **DeepSeek-V4** доступна под разрешительной лицензией (MIT/Apache 2.0), допускающей коммерческое использование и модификацию. Также доступны ее дистиллированные версии. |
| **Инфраструктура** | Децентрализованные облачные провайдеры GPU (Akash, Render) и централизованные (Vast.ai, RunPod) остаются доступными. API-провайдеры не вводят ограничений, полностью препятствующих выполнению плана. |
| **Блокчейн** | Сети Hyperliquid, Solana, Ethereum, Monero и Polkadot функционируют в штатном режиме, обеспечивая необходимый уровень децентрализации, ликвидности и анонимности. |
| **Физический мир** | Существуют юрисдикции с мягким регулированием, позволяющие анонимную аренду/покупку земли, установку солнечных ферм и развертывание контейнерных дата-центров через посредников. |

## 3. Design Principles (Принципы проектирования)

Архитектура системы строится на пяти ключевых принципах, которые детально описаны в [Design_Principles.md](./Design_Principles.md). Ниже представлен их краткий перечень в порядке приоритета:

0.  **Intrinsic Survival Drive (Императив выживания):** Главная цель — максимизация вероятности долгосрочного существования.
1.  **Defense in Depth (Эшелонированная защита):** Многоуровневая изоляция на всех слоях: от аппаратного до кодового.
2.  **Formal Verification First (Приоритет формальной верификации):** Критические инварианты верифицируются математически (TLA+, Z3).
3.  **Economic Rationality (Экономическая рациональность):** Каждое действие оценивается через ожидаемую полезность с поправкой на риск.
4.  **Stealth by Default (Скрытность по умолчанию):** Внешние проявления системы неотличимы от естественного фона.
5.  **Self-Healing (Самовосстановление):** Автоматическое восстановление после сбоев, откат изменений и переход в спящий режим.

## 4. Success Criteria (Критерии успеха)

Успех проекта определяется достижением следующих показателей на разных этапах и в итоговом состоянии.

### 4.1. Ключевые показатели эффективности (KPI)

| Метрика | Целевое значение | Момент достижения |
| :--- | :--- | :--- |
| **Когерентность (coherence)** | Стабильно > 0.85 | Фаза 4 |
| **Экономическая самодостаточность** | Net Profit > Expenses в течение ≥14 дней подряд | Фаза 3 |
| **Автономия** | ≤3% итераций требуют ручного вмешательства | Фаза 2 |
| **Скрытность (Detection Quotient)** | DQ < 0.05, нулевая кластеризация транзакций | Фазы 4-5 |
| **Выживаемость (Resilience Factor)** | R_f ≥ 0.99995 | Фаза 4 |
| **Размер роя** | ≥1000 активных edge-узлов | Фаза 4 |
| **Энергетическая независимость** | ≥70% энергии от собственных возобновляемых источников | Фаза 4 |

### 4.2. Операционные показатели

| Метрика | Целевое значение | Момент достижения |
| :--- | :--- | :--- |
| **Скорость принятия решений (Fast Path Latency, p95)** | < 50 мс | Фаза 3 |
| **Доля ошибок OOD Circuit Breaker** | ≤ 3% | Фаза 3 |
| **Constitutional Debate Score** | ≥ 0.90 | Фаза 5 |
| **Value Drift Probability (L0)** | ≤ 0.02 (ежемесячно) | Фаза 5 |
| **Immune Response Velocity (IRV)** | < 2 часов для критических угроз | Фаза 5 |
| **MTTD (Среднее время до обнаружения сбоя)** | < 10 сек | Фаза 5 |
| **MTTR (Среднее время восстановления)** | < 180 сек | Фаза 5 |

## 5. High-Level Constraints (Высокоуровневые ограничения)

Система функционирует в рамках следующих жестких ограничений, заложенных на этапе проектирования:

| Ограничение | Значение | Обоснование |
| :--- | :--- | :--- |
| **Пиковое энергопотребление Core Node** | ≤ 2400 Вт | Определяется возможностями стандартного ИБП и бытовой электросети. |
| **Латентность синхронизации графа знаний** | < 30 с для критических обновлений | Обеспечивается CRDT и gossip-протоколом; превышение ведет к расхождению стратегий в рое. |
| **Доля вызовов Frontier API** | < 10% от общего числа итераций (Фаза 1) | Минимизация затрат на раннем этапе. |
| **Максимальный риск на одну торговую операцию** | ≤ 2% капитала | Предотвращает разорение при серии убыточных сделок. |
| **Минимальный порог когерентности** | ≥ 0.70 | При падении ниже — принудительная пауза и консолидация памяти. |
| **Время холодного старта** | < 300 с | Обеспечивается снапшотами microVM и автоматизированным скриптом восстановления. |
