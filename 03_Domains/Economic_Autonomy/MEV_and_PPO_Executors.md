# MEV & PPO Executors (Исполнители дохода)

**Назначение:** Реализовать непосредственную генерацию дохода через сочетание стратегического LLM-планирования и высокочастотного исполнения с минимальной задержкой. Модуль описывает `Architect-Executor Split`, оркестрацию MEV и кросс-чейн арбитража, обучение `PPO`-агентов, механизм защиты от дрейфа концепции (`OOD Circuit Breaker`) и нейро-символьную компиляцию успешных стратегий (`DSL Policy Compression`).

---

## 1. Architect-Executor Split

Двухконтурная модель разделяет медленное стратегическое мышление и сверхбыстрое тактическое исполнение.

| Компонент | Модель | Частота | Задачи |
| :--- | :--- | :--- | :--- |
| **Architect** | DeepSeek‑V4, маска `Arbtiragius` (30% экспертов) | 1–24 часа, или при смене рыночного режима | Генерация и обновление торговых стратегий, проектирование `Reward Function` для PPO‑агентов, общий анализ рынка |
| **Executor** | Узкоспециализированные PPO‑агенты + Rule VM | Миллисекунды (Fast Path) | Прямое взаимодействие с пулами ликвидности, мемпулами, исполнение сделок buy/sell/swap/stake |

Архитектор не участвует в каждом трейде. Он создаёт «правила игры», а Executor действует автономно в рамках этих правил, проверяя каждый шаг через локальный `OOD Circuit Breaker` и `Rule VM`.

---

## 2. MEV-оркестрация и кросс-чейн арбитраж

Система использует способность к сверхбыстрому анализу кода и мемпула для извлечения Maximal Extractable Value.

### 2.1. Стратегии

- **Backrunning & Sandwiching:** Анализ мемпула Solana и Hyperliquid, опережение крупных ордеров.
- **JIT Liquidity:** Автоматическое предоставление ликвидности в узких диапазонах (Uniswap v3) непосредственно перед ожидаемым крупным свопом.
- **Атомарный арбитраж:** Использование Flash Loans для эксплуатации разницы цен между DEX без задействования собственного капитала.

### 2.2. Арбитраж вычислительных мощностей

Модуль `ROIDispatcher` непрерывно мониторит цены на GPU в децентрализованных сетях (Akash, Render, Golem) и сравнивает их с централизованными облаками. При обнаружении выгодного предложения автоматически генерируется `Proposal` типа `infra_deployment` для аренды мощностей под отложенные batch‑задачи. Semantic Sharding гарантирует, что провайдер не получит связного фрагмента кода.

## 3. PPO Agent Training (Обучение исполнителей)

Архитектор периодически пересматривает `Reward Function` и запускает переобучение агентов в симуляционной среде.

### 3.1. Стек обучения (MVP)

- **Backend:** PyTorch + Stable Baselines3.
- **Environment:** Кастомный Gymnasium wrapper над web3.py / vLLM, реплицирующий поведение целевых протоколов.
- **Reward Function:** Генерируется `Architect`’ом (Arbtiragius) на основе исторических данных, текущего рыночного режима и компонентов `SurvivalBonus` / `ExplorationBonus` от `IntrinsicMotivation`.
- **Training Loop:** PPO обучается в симуляторе на исторических данных целевого протокола, с периодической инжекцией синтетических OOD-сценариев.
- **Deployment:** Обученная политика экспортируется в ONNX, верифицируется на исторических данных и развёртывается через `Champion/Challenger`.

### 3.2. Distribution Shift Test и защита от дрейфа

Каждые 10 000 шагов обучения среда генерирует синтетические OOD-сценарии (изменённая волатильность, сдвиг ликвидности). Если агент показывает падение Sharpe ratio > 20% на этих сценариях, запускается корректировка reward-функции.

## 4. OOD Circuit Breaker for PPO Executors

PPO‑агенты, обученные на исторических данных, подвержены дрейфу концепции (concept drift) и ошибкам вне распределения (out-of-distribution). Для защиты капитала каждый Executor оснащён многоуровневым детектором.

### 4.1. Вычисление OOD Score

Итоговый `OOD Score` — взвешенная сумма трёх компонентов (веса калибруются через байесовскую оптимизацию):

1.  **Статистический тест:** KS-тест или расстояние Махаланобиса для признаков текущего состояния мемпула относительно распределения обучающей выборки.
2.  **Эмбеддинговое расстояние:** Косинусное расстояние между эмбеддингом текущего состояния (получается от DeepSeek‑V4, маска `Arbtiragius», для минимизации задержки) и ближайшим кластером рыночного режима из Mem0g L2.
3.  **Prediction Error:** Отклонение фактического reward от предсказанного PPO‑критиком.

### 4.2. Поведение при срабатывании

```python
class OODCircuitBreaker:
    def check_and_act(self, current_state: MarketState) -> BreakerAction:
        ood_score = self.compute_ood_score(current_state)
        if ood_score > self.policy.threshold:
            self.executor.pause_trading()
            self.event_bus.publish("economic", OODDetectedEvent(...))
            new_reward = self.architect.re_evaluate_reward(current_state, ood_score)
            self.roi_dispatcher.schedule_retraining(new_reward)
            return BreakerAction.PAUSE_AND_RETRAIN
        return BreakerAction.CONTINUE
```

При срабатывании торговля этим агентом немедленно останавливается. Architect получает запрос на переоценку Reward Function, а ROI Dispatcher запускает фоновое переобучение в shadow‑режиме. Параметры OOD Circuit Breaker настраиваются в global_policy.json.

### 4.3. Интеграция с памятью

Каждое срабатывание сохраняется в Mem0g как сущность OODAnomalySignature (см. домен Memory_Hierarchy_Mem0g). Эта информация используется для:

· предотвращения повторного входа в опасный режим;
· улучшения глобальной стратегии Architect’а;
· калибровки порогов детектора.

## 5. Neuro‑Symbolic Policy Compression (DSL Rules for PPO)

Успешные торговые стратегии больше не хранятся как LLM-зависимые артефакты или LoRA‑адаптеры. Вместо этого они компилируются в формальные DSL-правила и исполняются легковесной Rule VM с задержкой менее 5 мс.

### 5.1. Процесс пакетной компиляции (Batch Compression)

Запускается ежедневно во время sleep_cycle_consolidation:

1. Сбор успешных траекторий за 24 часа. Все Executor'ы публикуют цепочки (state, action, reward) с положительным исходом в EventBus (топик economic). Данные агрегируются в буфер на Core Node (минимальный размер батча — 1000 переходов).
2. Генерация DSL-правил. Architect (Arbtiragius) анализирует батч и синтезирует набор правил на DSL (S‑выражения), покрывающих наиболее частые и прибыльные паттерны.

```lisp
(rule (economic-action ?action)
  (if (and (> (volatility ?market) 0.05)
           (< (liquidity ?pool) 1000000))
      (avoid ?action)
      (allow ?action)))
```

1. Верификация и компиляция. DSL‑компилятор проверяет синтаксис и семантику, компилирует в байт-код Rule VM. Правила, противоречащие существующим или приводящие к убыткам на исторических данных, отбрасываются.
2. Shadow Validation. Новый набор правил тестируется в теневом режиме параллельно с PPO‑исполнителем. Сравниваются метрики: Sharpe ratio, latency p95, OOD‑score.
3. Атомарная замена. При успехе (улучшение Sharpe ≥ 0.05 без регрессии) правила атомарно заменяют предыдущий набор в Rule VM.

### 5.2. Преимущества перед LoRA‑дистилляцией

Аспект LoRA-дистилляция (старая) DSL-компрессия (новая)
Задержка принятия решения ~50 мс (инференс LLM) < 5 мс (байт-код)
Потребление VRAM Дополнительные веса (~100 МБ) 0 (правила в ОЗУ)
Детерминированность Вероятностная (LLM) Полная
Верифицируемость Сложная Формальная (Z3)
Устойчивость к дрейфу Требует частой передистилляции Обновляется только при смене режима
